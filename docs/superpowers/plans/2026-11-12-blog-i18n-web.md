# Blog i18n on the personal website Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `lequoctrung.vn` blog lists and articles follow the page locale against `blog-api`, including translated slugs, without breaking VI-only posts or a site that has not enabled `i18n` yet.

**Architecture:** Keep chrome i18n (`app/[lang]`, `localePath`, dictionaries). Teach `lib/blog.ts` to send `?locale=`, fall back on 400/404, and resolve the correct slug. Pages and discovery routes pass the page locale through. Language switcher on an article uses `translations[]`. No new library.

**Tech Stack:** Next.js 16 App Router, TypeScript, `node:test` via `tsx --test`, existing Go blog-api (`?locale=`, `translations[]`).

**Spec:** `docs/superpowers/specs/2026-11-12-blog-i18n-web-design.md` (this repo). URL chrome: `docs/superpowers/specs/2026-10-06-i18n-vietnamese-design.md`. Engine contract: `blog-api/docs/superpowers/specs/2026-11-02-multitenant-design.md` §16.1.

## Global Constraints

- Locales exactly `en` | `vi`. Page default `en`. Engine default `vi`.
- No new runtime dependencies.
- Branch `feature/blog-i18n-web` off `develop`. Never commit to `main` or `develop`.
- Conventional commits: `feat(blog-i18n): …`.
- `pnpm --filter website test`, `typecheck`, `lint` stay green. Do not add a browser fetch to `blog-api`.
- `lang` on post title/excerpt/body/cards is `post.locale`, never a hardcoded `"vi"`.
- Server-only data: RSC and `app/actions/blog.ts`.

## Review Focus

1. `GET ?locale=en` returns 400 because site `personal` still has `i18n` off → every fetcher retries `locale=vi` and the page still renders.
2. Visitor opens `/blog/{vi-slug}` after i18n is on and an EN translation exists with a different slug → 308 to `/blog/{en-slug}`.
3. Visitor opens `/blog/{vi-slug}` when only VI is published → 200, body `lang="vi"`, canonical `/blog/{vi-slug}`, no hreflang pair.
4. Language switcher on a translated article uses the other slug, not `localePath(other, currentPath)`.
5. `loadMorePosts` on `/blog` (English chrome) requests `locale=en` so page 2 matches page 1.

### Task 1: Locale-aware blog client

**Files:**
- Modify: `apps/website/lib/blog.ts`
- Modify: `apps/website/lib/blog.test.ts`

**Interfaces:**
- Consumes: `Locale` from `apps/website/lib/i18n/config.ts`
- Produces:
  - `postsQuery(params: { locale: Locale; tag?: string; page?: number; limit?: number }): string` — path+query after `/posts`
  - `translationSlug(post: { translations: { locale: string; slug: string }[] }, locale: Locale): string | null`
  - `fetchPosts(params: { locale: Locale; tag?: string; page?: number; limit?: number; revalidate?: number }): Promise<{ posts: PostSummary[]; meta: PaginationMeta }>`
  - `fetchPost(slug: string, locale: Locale, opts?: { revalidate?: number }): Promise<PostDetail | null>`
  - `fetchRelatedPosts(slug: string, locale: Locale, opts?: { limit?: number; revalidate?: number }): Promise<PostSummary[]>`
  - `fetchAdjacentPosts(slug: string, locale: Locale, opts?: { revalidate?: number }): Promise<AdjacentPosts>`
  - `fetchAllPosts(locale: Locale, revalidate?: number): Promise<PostSummary[]>`
  - `resolvePost(slug: string, pageLocale: Locale, opts?: { revalidate?: number }): Promise<{ post: PostDetail; redirectTo: string | null; hrefs: Record<Locale, string> } | null>`

`resolvePost` rules (spec): try `pageLocale`, then the other locale; if the served post has `translationSlug(post, pageLocale)` different from `slug`, `redirectTo = localePath(pageLocale, /blog/{that})`; else `redirectTo = null`. `hrefs[L] = localePath(L, /blog/{translationSlug(post, L) ?? slug})`.

400 handling: any helper that sets `locale` retries once with `"vi"` when the response status is 400.
